# Облачное исследование: решение и интеграция в v4

Полные данные с URL источников: `CLOUD_RESEARCH_RAW.md` (216 строк, всё по
официальным страницам 2025–2026, исследования выполнены 2026-10-18).
Здесь — выжимка и решение.

## 1. Что проверялось

- NotebookLM (Gemini Notebook): публичного API нет; Video Overviews экспортируются
  вручную; автоматизация браузера — риск аккаунта. Для конвейера 4/день неприменим.
- Облачные видео-API «бесплатно»: Shotstack (sandbox с водяным знаком),
  JSON2Video/Creatomate/Bannerbear (разовые trial-кредиты), Cloudinary (25
  кредитов/мес — мало), CloudConvert (конвертер, не редактор). Итог: бесплатных
  продакшн-квот на 120 роликов/мес НЕ существует. Remotion бесплатен как ПО
  (лицензия для частных лиц/команд ≤3), но compute оплачивается отдельно.
- Always-free compute: Oracle Cloud Always Free ARM (2 OCPU/12 ГБ после урезания
  в 2026, риск reclaim простаивающих VM и «out of capacity»), Fly.io (free-VM
  для новых аккаунтов отменён), Cloud Run (требует биллинг-аккаунт), HF Spaces
  (засыпает).
- **GitHub Actions в public-репозитории: минуты остаются бесплатными в 2026**
  (официально); лимит 6 ч/джоба; cron ненадёжен (задержки) — триггер лучше
  слать из внешнего «мозга».
- TTS: Azure Speech F0 — 500k симв./мес, но коммерческие права на вывод —
  только paid tier (Product Terms Microsoft); ElevenLabs free — без коммерческой
  лицензии; **edge-tts — неофициальный** (риск блокировок; для регулярного
  продакшена — или локальный Piper (MIT, ru_RU есть), или Azure paid).
- YouTube Data API v3: с июня 2026 videos.insert считается собственным бакетом
  **100 вызовов/день** (не «1600 units из 10000», как раньше); videos.list = 1
  unit. 4 загрузки/день — с запасом. OAuth-приложение держать в Production
  (Testing = refresh-токен живёт 7 дней).
- Telegram Bot API: sendVideo ≤50 МБ (наши ≤15 МБ влезают), rate-лимиты для
  4 постов/день несущественны.
- Хранение: GitHub Releases (≤2 ГиБ/файл, без суммарного лимита) или Cloudflare R2
  (10 ГБ free без egress).

## 2. Вердикт по схеме ТЗ

### «Облачный генератор отдельного фрагмента»
Реально только платно (Shotstack/JSON2Video/…) или вручную (NotebookLM export).
Качество/лицензии/квоты для 4 выпусков в сутки не сходятся. В v4 не включаем,
но архитектура сменных адаптеров (`publish/…`, `media/tts.py`) позволяет
подключить генератор фрагментов позже без переделки ядра.

### «Полный облачный цикл» (работает при выключенном ноутбуке)
Единственная реально бесплатная связка на октябрь 2026:

**A (рекомендуемая, гибрид с резервом):**
- «Мозг» — Oracle Always Free VM (ARM 2/12): тот же код `tubecook` (service),
  Telegram-поллинг, SQLite, планировщик. Риск: reclaim — держать периодическую
  нагрузку и мониторинг.
- Рендер — GitHub Actions (public repo): воркфлоу `render.yml`, триггер
  `repository_dispatch` от VM (cron в Actions ненадёжен). Секреты (токены) —
  в GitHub Secrets; артефакты/видео — Releases или R2.
- Публикация — из VM (Telegram Bot API) и из Actions (YouTube API, OAuth-токен
  в Secrets) — либо всё из VM после скачивания артефакта.
- Полностью бесплатно; сложность выше; требует разовой ручной настройки
  (OAuth, токены, права) и алертов на простои.

**B (текущая, основная):** локальный HP — как сейчас, нулевая настройка облака;
облако (Actions) — резервный рендер-бёрст при поломке ноутбука.

**C (минимальный):** только GHA + состояние в git — хрупко, не рекомендуется
  как основное.

Качество видео локального рендера (FFmpeg + процедурная графика) сопоставимо
облачным шаблонным API; «облачное» преимущество — только доступность при
выключенном ноутбуке, цена — сложность и риски ToS/квот.

## 3. Как подключить вариант A к v4 (точные шаги, БЕЗ создания аккаунтов)

1. Public-репозиторий с кодом v4 (секреты не коммитить!).
2. В репо добавить `.github/workflows/render.yml`:
   `on: repository_dispatch [render]` → шаги: checkout, установка ffmpeg +
   pip, `python -m tubecook.cli render job.json --engine edge` → загрузка
   артефакта (actions/upload-artifact) или Release.
3. На VM (Oracle) развернуть тот же `tubecook service`; после рендера
   (или вместо него) отправлять задание в Actions:
   `curl -X POST -H "Authorization: token <PAT>" \
   https://api.github.com/repos/<owner>/<repo>/dispatches -d \
   '{"event_type":"render","client_payload":{"job_id":"…"}}'`.
4. Токены: TELEGRAM_BOT_TOKEN — на VM в `.env`; YouTube OAuth — один раз
   локально (`cli oauth-youtube`), `token.json` положить в VM/GH Secrets.
5. YouTube-загрузку можно вести из VM (библиотеки google в requirements).
6. Обязательные чек-листы: Actions-ToS (порог «злоупотребления» не опубликован —
   держать разумную нагрузку), Oracle reclaim-мониторинг, алерты в Telegram
   при простое конвейера >N часов.

## 4. Что не обещаем

- Не обещаем «бесплатно навсегда»: условия Oracle/GitHub/YouTube меняются
  (пример — урезание Oracle ARM в 2026); цифры квот сверяйте в консолях.
- Не используем обходы капч/лимитов; автоматизацию браузерных интерфейсов
  (NotebookLM) не внедряем — риск аккаунта Google, где и YouTube-канал.
- Полный отказ от ноутбука требует ручной разовой настройки (аккаунты, OAuth,
  PAT) — выполнить владельцу; Z.ai аккаунты не создаёт и не оплачивает.

## 5. Влияние на текущий пакет

Основной путь поставки v4 — локальный (вариант B): он уже работает и
проверен тестами/рендерами. Облачный вариант A — подключаемая надстройка
(скрипт-триггер + workflow), не блокирует локальную работу; в коде есть всё
необходимое (CLI `render` без БД, артефакты самодостаточны, TTS-кэш).
