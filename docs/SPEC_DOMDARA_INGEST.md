**Версия спецификации:** 1.0.0  
**Дата:** 19 октября 2026 г.  
**Контекст проекта:** Tubecook v4.0.0-rc1 (автономный видеоконвейер на Python/FFmpeg)

## 1. Назначение и цель модуля

Реализовать в Tubecook v4 автономный модуль сбора статей с сайта кооператива «Домдара» (`http://domdara.org/feed/`) — `tubecook.ingest.domdara`.

Модуль должен:
1. Автоматически считывать новые публикации с `domdara.org` (заголовок, текст, ссылки, номера судебных дел, изображения).
2. Трансформировать их в формат заданий Tubecook v4 (`JobPayload` / `#TUBECOOK_JOB v4`).
3. Помещать в единую очередь SQLite с гарантией дедупликации, хронологического порядка и приоритета.
4. Работать устойчиво к периодическому выключению/сну ноутбука (offline-first).
5. Обеспечивать независимый учет публикации в Telegram и YouTube.
6. Соблюдать интервал выпусков (1 ролик раз в 6 часов, Европа/Киев), исключая залповый выброс после простоя.
7. Предоставить первый собранный ролик Сергею на проверку до включения автоматической публикации.

## 2. Анализ существующего решения и архитектурный выбор

На продакшн-ВМ (`agrobot-prod`) круглосуточно работает демон `bot_skaner_saitov` (Telethon MTProto + RSS poller, коммит `4ba2e5c` в `Sereban-glitch/bot_skaner_saitov`).

### Особенности источника `domdara.org` (выявленные на практике):
- **Протокол:** `http://domdara.org/feed/`. **Важно:** SSL-сертификат на `https://domdara.org` сломан/просрочен. Обязательно использовать `http://` или отключать проверку SSL (`ssl=False` / `verify=False`).
- **Формат:** WordPress 5.4 RSS 2.0 (по 10 статей на страницу). Пагинация: `http://domdara.org/feed/?paged=N`.
- **Периодичность публикаций:** новые статьи появляются раз в 2–7 дней.
- **Структура контента:** правозащитные материалы, решения судов, споры с коммунальными службами и ТЦК.
- **Ключевой маркер достоверности:** номер судебного дела (регулярное выражение `\d{3,4}/\d+/\d{2,4}`, например `№ 280/8165/23`).
- **Ассеты:** `og:image` в шапке статьи, изображения в `wp-content/uploads/`, ссылки на YouTube Shorts внутри текста.

### Выбор архитектуры: Прямой сбор на ноутбуке (Вариант А) vs Мост через ВМ (Вариант Б)
- **Выбран Вариант А (прямой сбор на ноутбуке):**
  - **Обоснование:** Ноутбук автономен. Прямой опрос RSS не зависит от статуса ВМ, сетевых туннелей или состояния MTProto-сессии. Не создает нагрузки на чужие сервисы ВМ и не требует изменения боевых демонов. Логика парсинга переносится из `bot_skaner_saitov/bridge.py` без изменений.

## 3. Требования к модулю `tubecook.ingest.domdara`

### 3.1. Сбор метаданных и контента статьи
1. **Запрос ленты:**
   - URL: `http://domdara.org/feed/`
   - User-Agent: `Mozilla/5.0 Codex Bridge`
   - Таймаут: 15 секунд, до 3 повторных попыток с экспоненциальной задержкой.
2. **Парсинг XML (ElementTree):**
   - `<title>` -> название статьи.
   - `<link>` -> каноническая ссылка.
   - `<guid>` -> уникальный идентификатор (например, `http://domdara.org/?p=5786`).
   - `<pubDate>` -> дата публикации (RFC 822 / RFC 2822), приводится к UTC/ISO-8601.
   - `<description>` и `<content:encoded>` -> текст.
3. **Обогащение со страницы статьи (`fetch_article_details`):**
   - Загрузка HTML статьи по `<link>`.
   - Извлечение `og:image` (если есть) или первого изображения из блока контента (`wp-content/uploads/`).
   - Извлечение номеров судебных дел через regex `(?:дело|справа|№)\s*[:№]?\s*(\d{3,4}/\d+/\d{2,4})` или `\b\d{3,4}/\d+/\d{2,4}\b`.
   - Если в статье встроено YouTube Shorts видео (`https://www.youtube.com/shorts/...`), ссылка сохраняется в метаданных источника.
4. **Формирование сценария и выжимки для ролика:**
   - Если подключен AI-редактор: генерация 4–6 сцен (крючок, прецедент/суть, номер дела, решение суда, вывод для людей).
   - Если AI недоступен: структурная нарезка по абзацам (метод обратной пирамиды) с гарантированным включением номера дела.

---

### 3.2. Холодный старт и ограничение архива (Initial Boundary)
- При первом запуске на чистой базе конвейер **не должен** выкачивать архив статей за прошлые годы.
- Конфигурация `domdara_initial_lookback_days: int = 3` (по умолчанию 3 дня).
- Режимы инициализации:
  - `seed_latest_only`: зафиксировать текущий самый свежий GUID как исходную точку, в очередь ничего не добавлять, ждать новые статьи.
  - `lookback`: добавить статьи только за последние `N` дней (не старше `domdara_initial_lookback_days`).

---

### 3.3. Устойчивость к оффлайну и восстановление очереди (Backlog Catch-Up)
Ноутбук часто выключен по несколько суток.
1. При запуске службы модуль считывает из `meta` в SQLite:
   - `domdara_last_seen_guid`
   - `domdara_last_seen_date`
2. Модуль опрашивает `http://domdara.org/feed/`. Если между `last_seen_guid` и текущей лентой пропущено более 10 статей, запрашиваются следующие страницы ленты (`?paged=2`, `?paged=3`...) до достижения `last_seen_guid` или предельного окна `max_catchup_pages: int = 5`.
3. Все найденные новые статьи фильтруются по `dedupe_key`.
4. **Критическое требование:** Пропущенные статьи добавляются в очередь **строго в хронологическом порядке от старых к новым** (`ORDER BY pubDate ASC`), чтобы хронология прецедентов не нарушалась.

---

### 3.4. Защита от дубликатов (Deduplication)
- Ключ дедупликации `dedupe_key`: `domdara:guid:{guid_or_id}` (дополнительно сохраняется канонический URL).
- Уникальный индекс в SQLite: `CREATE UNIQUE INDEX IF NOT EXISTS idx_jobs_dedupe ON jobs (dedupe_key)`.
- Попытка повторной вставки той же статьи игнорируется (`INSERT OR IGNORE`) или обновляет существующую запись, если статус был `failed`.

---

### 3.5. Интервал публикаций и защита от залпового сброса (Pacing)
- Если за время сна ноутбука накопилось несколько статей (например, 3 штуки):
  - Конвейер **НЕ публикует их все сразу**!
  - Параметр `catchup_max: int = 1` в `Scheduler`.
  - Статьи распределяются по слотам публикаций: `00:00`, `06:00`, `12:00`, `18:00` Europe/Kyiv (интервал 6 часов).
  - Свежесть статьи проверяется перед рендером: если новость просрочена дольше `article_ttl_days: int = 14`, выставляется статус `stale` с уведомлением администратора.

---

### 3.6. Приоритеты источников (Multi-source Priority Queue)
Очередь SQLite едина для всех источников. При выборке следующего задания на рендер/публикацию применяется весовая сортировка:
1. `Priority.MANUAL` (вес 100): темы Сергея (через Telegram-бота или CLI). Всегда идут первыми вне очереди.
2. `Priority.AI_NEWS` (вес 50): подборка новостей ИИ от Саши.
3. `Priority.DOMDARA` (вес 30): новости сообщества Домдара.

---

### 3.7. Независимый учет Telegram и YouTube (Publish Target Isolation)
Таблица `publish_targets (job_id, target, state, attempts, last_error, result_ref, updated_at)`:
- Каждая площадка публикуется независимо (`target='telegram'`, `target='youtube'`).
- Если Telegram опубликован успешно, а YouTube упал по квоте или сети:
  - Статус Telegram: `published`, `result_ref='<telegram_message_id>'`.
  - Статус YouTube: `failed`, `last_error='<error>'`.
  - При повторной попытке или перезапуске служба **не отправляет видео в Telegram повторно**!
- **Предпроверка перед повторной публикацией:**
  - Перед вызовом Telegram API проверяется наличие `result_ref`.
  - Перед загрузкой на YouTube проверяется, нет ли уже видео с таким `client_reference_id` / тегом `job_id` в метаданных канала.

---

### 3.8. Ручной контроль первого ролика (Human-in-the-loop)
- До явного одобрения владельца:
  - Автоматическая публикация в канал `@svobodnye_ludi_zp` и YouTube-канал отключена (`autonomous_mode = False`, `require_approval = True`).
  - Первый ролик рендерится полностью, валидируется hardware-замером, и ссылка/видеофайл отправляется Сергею в личные сообщения админа (`ADMIN_IDS`).
  - Только после команды `/approve <job_id>` или смены конфигурации включается публикация.

## 4. Конфигурационные параметры (`tubecook/config.py`)

```python
# Domdara Ingest
domdara_enabled: bool = True
domdara_feed_url: str = "http://domdara.org/feed/"
domdara_poll_interval_minutes: int = 30
domdara_initial_lookback_days: int = 3
domdara_seed_mode: str = "lookback"  # "lookback" | "latest_only"
domdara_article_ttl_days: int = 14
domdara_user_agent: str = "Mozilla/5.0 Tubecook Ingest (Linux x86_64)"

# Publishing & Pacing
slots: tuple[int, ...] = (0, 6, 12, 18)  # Europe/Kyiv
catchup_max: int = 1
require_approval: bool = True  # True до проверки первого ролика Сергеем
autonomous_mode: bool = False
```

## 5. План приёмки и тестов

1. **Unit-тесты:**
   - Парсинг сырого XML `domdara.org` (фикстура с реальной статьи про Водоканал и ст. 336 ККУ).
   - Извлечение номеров судебных дел разных форматов (`280/8165/23`, `№753/19985/25`).
   - Извлечение `og:image` и картинок.
   - Дедупликация и сортировка от старых к новым (`test_chronological_sort`).
2. **Integration-тесты:**
   - Симуляция выключения на 48 часов: добавление 3 пропущенных статей, проверка распределения по будущим слотам (по 1 в слот с шагом 6 ч).
   - Симуляция сбоя YouTube при успешном Telegram: повторный тик не должен дублировать публикацию в Telegram.
   - Проверка флага `require_approval`: отсутствие автоматической отправки без подтверждения.
3. **Сквозной запуск (Dry-Run):**
   - Запуск `tubecook domdara ingest --dry-run`: вывод в консоль найденных статей, извлеченных номеров дел и картинок без изменения БД.
   - Запуск `tubecook domdara run-once`: постановка первой статьи в очередь, рендер первого тестового видео на Intel HD 520 (VA-API), отправка превью Сергею.
